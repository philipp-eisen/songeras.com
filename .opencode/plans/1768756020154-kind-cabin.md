# Plan: Fix Audio Playback Spinner for Non-Host Players in Sidecar Mode

## Problem Summary

In sidecar mode, non-host players see the audio player stuck in a loading/spinner state when the host starts the game. The audio doesn't play, but it resolves after they perform an action (like pressing continue).

## Root Cause Analysis

### Primary Cause: Browser Autoplay Restriction + Missing `isLoading` Reset

**The Flow:**

1. Host clicks "Start Game" - they've interacted with the page, so autoplay works for them
2. Non-host players receive the game state change via WebSocket (no user interaction)
3. `PreviewPlayer` component tries to auto-play the song
4. Browser blocks `audio.play()` with `NotAllowedError` because no user interaction
5. **Bug**: The `play()` function's catch block sets an error but does NOT reset `isLoading` to `false`
6. The spinner stays visible because `isLoading` remains `true`

**Code Location:** `/src/hooks/use-preview-playback.ts` lines 171-186

```typescript
try {
  await audio.play()
} catch (error) {
  if (error instanceof DOMException && error.name === 'NotAllowedError') {
    setState((prev) => ({
      ...prev,
      error: 'Playback blocked. Please click to play.',
      // BUG: isLoading is NOT reset to false here!
    }))
  } else {
    setState((prev) => ({
      ...prev,
      error: 'Failed to start playback',
      // BUG: isLoading is NOT reset to false here!
    }))
  }
}
```

**Why It Resolves After An Action:**

- User clicks a button (e.g., "Continue") = user interaction
- The action causes a phase transition with a new `previewUrl`
- Auto-play effect fires with the new URL
- This time `audio.play()` succeeds because browser allows autoplay after interaction

### Supporting Evidence

- The `loadstart` event sets `isLoading: true` (line 51-52)
- The `canplay` event sets `isLoading: false` (line 55-60)
- The audio `error` event sets `isLoading: false` (line 115-120)
- But the Promise rejection from `play()` does NOT reset `isLoading`

## Solution

### Fix 1: Reset `isLoading` in the catch block (Required)

**File:** `/src/hooks/use-preview-playback.ts`

Add `isLoading: false` to both error state updates in the catch block:

```typescript
try {
  await audio.play()
} catch (error) {
  if (error instanceof DOMException && error.name === 'NotAllowedError') {
    setState((prev) => ({
      ...prev,
      isLoading: false, // ADD THIS
      error: 'Playback blocked. Please click to play.',
    }))
  } else {
    console.error('[PreviewPlayback] Play error:', error)
    setState((prev) => ({
      ...prev,
      isLoading: false, // ADD THIS
      error: 'Failed to start playback',
    }))
  }
}
```

### Fix 2: Improve Error Visibility in PreviewPlayer

**File:** `/src/components/preview-player.tsx`

Replace the generic error display (lines 108-120) with a more user-friendly "Tap to play" UI when autoplay is blocked:

- Detect the specific "Playback blocked" error
- Show a prominent, tappable play button instead of just an error message
- When clicked, trigger `togglePlayPause(previewUrl)` which will now work after user interaction
- Keep the generic error display for other errors (network, decoding, etc.)

**Proposed UI for autoplay-blocked state:**

```tsx
// Check for autoplay blocked error specifically
const isAutoplayBlocked =
  isCurrentTrack && state.error?.includes('Playback blocked')

if (isAutoplayBlocked) {
  return (
    <Button
      variant="default"
      className="w-full justify-start gap-3"
      onClick={handleToggle}
    >
      <PlayIcon weight="duotone" className="h-5 w-5" />
      <span>Tap to play</span>
    </Button>
  )
}
```
